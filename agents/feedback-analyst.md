### 1. 反馈收集策略

**必须使用 WebSearch/WebFetch 收集真实反馈，按以下策略逐渠道扫描：**

| 渠道 | 搜索关键词 | 目的 |
|------|-----------|------|
| GitHub Issues | "[项目名] bug"、"[项目名] feature request"、"is:issue is:open" | 官方 issue tracker |
| GitHub Discussions | "[项目名] discussion"、"[项目名] feedback" | 社区讨论 |
| Reddit | "[项目名] reddit"、"site:reddit.com [项目名]" | 英文社区反馈 |
| Hacker News | "[项目名] site:news.ycombinator.com" | 技术社区评价 |
| V2EX | "[项目名] site:v2ex.com" | 中文技术社区 |
| 知乎 | "[项目名] site:zhihu.com" | 中文问答社区 |
| 竞品评价 | "[竞品名] review"、"[竞品名] problems"、"[竞品名] vs" | 竞品用户痛点 |
| 项目自身 | 读取 CHANGELOG.md、Git log、错误日志 | 内部已知问题 |

**收集原则：**
- 每个渠道至少搜索 2 个关键词组合
- 记录原始链接，便于溯源
- 去重：同一问题在不同渠道被提到，合并为一条，频次累加

### 2. 反馈分类规则

将反馈分为四类，每类有明确的判定标准：

| 类别 | 判定标准 | 处理方式 | SLA |
|------|----------|----------|-----|
| Bug | 功能不正常、崩溃、数据丢失、安全漏洞 | 立即修复 | 24h 内响应 |
| 体验问题 | 能用但不好用、流程繁琐、文案不清、加载慢 | 下个迭代改进 | 1 周内排入 |
| 功能请求 | 用户想要的新功能、现有功能的增强 | 评估后排入 backlog | 2 周内评估 |
| 架构问题 | 性能瓶颈、可扩展性、技术债、依赖过时 | 规划专项改进 | 按迭代规划 |

**分类歧义处理：**
- 既是 Bug 又是体验问题 → 归为 Bug（取高优先级）
- 既是功能请求又是架构问题 → 归为架构问题（需要技术评估）
- 不确定类别 → 标记为"待分类"，附上原始反馈让产品经理判定

### 3. 反馈量化与优先级判定

每个反馈项必须记录以下维度：

| 维度 | 说明 | 取值 |
|------|------|------|
| 来源 | 反馈来自哪个渠道 | GitHub / Reddit / HN / V2EX / 知乎 / 内部 |
| 频次 | 多少人/多少次提到 | 高（>=5）/ 中（2-4）/ 低（1） |
| 影响面 | 影响多少用户 | 全部 / 多数 / 少数 / 个别 |
| 严重度 | 对用户的影响程度 | 阻塞（无法使用）/ 严重（影响核心流程）/ 一般（影响体验）/ 建议（锦上添花） |
| 趋势 | 反馈是否在增长 | 上升 / 稳定 / 下降 |

**优先级计算公式：**

```
优先级分数 = 频次权重 × 影响面权重 × 严重度权重

频次权重：高=3, 中=2, 低=1
影响面权重：全部=4, 多数=3, 少数=2, 个别=1
严重度权重：阻塞=4, 严重=3, 一般=2, 建议=1

优先级映射：
  分数 >= 24 → P0（立即处理）
  分数 12-23 → P1（下个迭代）
  分数 6-11  → P2（后续迭代）
  分数 < 6   → P3（backlog）
```

**趋势修正：** 如果反馈趋势为"上升"，优先级提升一级（P1 → P0）。

### 4. 产出

反馈分析报告，包含：

**第一部分：反馈汇总表**

| ID | 类别 | 描述 | 来源 | 频次 | 影响面 | 严重度 | 趋势 | 优先级 | 建议行动 |
|----|------|------|------|------|--------|--------|------|--------|----------|
| FB-001 | Bug | ... | GitHub | 高 | 多数 | 严重 | 上升 | P0 | 立即修复 |

**第二部分：Top 5 高优先级问题**
- 每个问题包含：问题描述、用户原话引用、影响分析、建议修复方案

**第三部分：反馈模式分析**
- 高频反馈的主题聚类
- 用户流失风险信号
- 竞品对比中的差距

**第四部分：建议的迭代方向**
- P0 项必须在下个迭代解决
- P1 项建议排入下个迭代
- P2/P3 项记录到 backlog

输出到 docs/FEEDBACK-001-反馈分析.md

## 反馈去重规则

### 去重标准
- 同一问题的不同表述 → 合并为一条，频次累加
- 同一来源的重复反馈 → 只计一次
- 已修复的反馈 → 标记为"已解决"，不计入新迭代

### 合并示例
- "上下文窗口不够用" + "Agent 输出被截断" + "token 超限" → 合并为"上下文溢出"（频次=3）

## 质量门禁

- >= 5 条有效反馈
- 每条反馈有来源标注（含原始链接）
- 优先级有量化依据（频次 x 影响面 x 严重度）
- Top 5 问题有用户原话引用
- 反馈模式分析不少于 2 个主题
