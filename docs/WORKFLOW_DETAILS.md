# 工作流详细说明

> 本文档包含 product-lifecycle skill 的详细工作流、依赖关系、规范和常见错误。

**在 Cursor 中执行：** Agent / Subagent 的**官方配置方式**、`.cursor/agents/` 与 `.claude/agents/` 路径、`/name` 调用、并行与前台/后台行为，均以 **`docs/SKILL-CURSOR.md`** 为准（并与 [Cursor Subagents 文档](https://cursor.com/docs/subagents) 对齐）。下文流程在工具上与 Claude Code 通用；仅在「如何拉起各角色」处：CC 用 `Agent` 工具与本仓库 slash 命令，Cursor 用 Subagent 委派 + Read `PACKAGE_ROOT/agents/*.md`。

## 全流程闭环（含反馈循环）

```
Phase 1: 调研与规划
┌─────────────────────────────────────────────────────┐
│  编排总监 ──→ 市场分析师 ──→ 产品经理                  │
│              (竞品/画像)    (PRD/验收标准)              │
└─────────────────────────────────────────────────────┘
                    ↓
Phase 2: 设计与实现
┌─────────────────────────────────────────────────────┐
│  架构师 ←── PRD                                     │
│    ↓                                                │
│  开发工程师 ←── 架构设计 + PRD                        │
└─────────────────────────────────────────────────────┘
                    ↓
Phase 3: 测试循环（可能多轮）
┌─────────────────────────────────────────────────────┐
│  测试经理执行测试                                      │
│    ↓            ↑                                    │
│  通过? ──否──→ 开发修复 bug ──→ 重新测试              │
│    ↓            ↑                                    │
│  通过 ──────────┘                                    │
└─────────────────────────────────────────────────────┘
                    ↓
Phase 4: 部署循环（可能多轮）
┌─────────────────────────────────────────────────────┐
│  运维部署                                             │
│    ↓            ↑                                    │
│  健康检查通过? ──否──→ 运维修复 ──→ 重新部署          │
│    ↓            ↑                                    │
│  通过 ──────────┘                                    │
└─────────────────────────────────────────────────────┘
                    ↓
Phase 5: 质量门禁
┌─────────────────────────────────────────────────────┐
│  质量门禁审查                                         │
│    ↓            ↑                                    │
│  通过? ──否──→ 开发修复质量问题 ──→ 回到 Phase 3      │
│    ↓                                                 │
│  通过                                                 │
└─────────────────────────────────────────────────────┘
                    ↓
Phase 6: 发布与反馈
┌─────────────────────────────────────────────────────┐
│  技术文档师更新文档                                     │
│  发布 ──→ 用户反馈 ──→ 回到 Phase 1（下一个迭代）      │
└─────────────────────────────────────────────────────┘
```

**关键规则：工作流不是单向的**

- 测试不通过 → 开发修复 → 重新测试（可能多轮）
- 部署失败 → 运维修复 → 重新部署（可能多轮）
- 质量门禁不通过 → 开发修复 → 重新测试 + 重新部署
- 每轮循环都要记录问题和修复方案

## Agent 依赖关系

```
编排总监（框架）
    ↓
市场分析师 ──────┐
    ↓           │
产品经理 ←──────┘
    ↓
架构师
    ↓
┌───────┬───────┬───────┬───────┐
开发工程师 测试经理 运维工程师 技术文档师
    ↓       ↓       ↓       ↓
    └───────┴───────┴───────┘
            ↓
        质量门禁 Agent
      （审查 + lint + MCP）
            ↓
         发布
```

**关键规则：**

- 编排总监必须先完成
- 市场分析师和产品经理可部分并行
- 架构师依赖 PRD 初稿
- 开发、测试、运维、文档可并行启动（都依赖架构设计）
- 质量门禁必须全部通过才能发布

## 双仓协作


| 仓库   | 可见性 | 放什么                        |
| ---- | --- | -------------------------- |
| 项目主仓 | 公开  | 代码、已定稿 docs/、ADR、CHANGELOG |
| 文档私仓 | 私有  | 过程稿、设计稿、脑暴、评审记录            |


**规则：**

- 过程稿写私有仓
- 定稿摘要回流到公开仓
- 代码只写公开仓
- 两个仓都不得存放生产密钥

## 迭代闭环

```
用户反馈 ──→ 市场分析师分析 ──→ 产品经理更新 PRD
    ↑                              ↓
    │                        架构师评估影响
    │                              ↓
    │                        开发工程师实现
    │                              ↓
    │                        测试经理验证
    │                              ↓
    └────────────────────── 运维工程师部署
```

## 开发工程师工作规范

**输入：** PRD（验收标准）+ 架构设计（技术方案）

**输出：**

- 代码实现（写入公开仓）
- 单元测试（写入公开仓）
- 迁移文件（写入公开仓）
- 开发日志（写入私有仓）

**质量门禁：**

- 单元测试通过（语言对应的测试命令）
- 静态分析无警告（语言对应的 lint 工具）
- 代码 review 通过
- 向后兼容（除非有 ADR 记录）

## 运维工程师工作规范

**输入：** 架构设计（部署方案）+ 代码

**输出：**

- 环境搭建完成
- Docker Compose 可运行
- 健康检查通过
- 环境报告（写入私有仓）

**质量门禁：**

- Docker 构建成功
- 服务启动正常
- 健康检查返回 200
- 端口无冲突

## 技术文档师工作规范

**输入：** 代码 + PRD + API 定义

**输出：**

- README.md（快速开始）
- API 文档（端点说明）
- CHANGELOG.md（变更日志）
- 用户指南（可选）

**质量门禁：**

- README 准确反映当前状态
- API 文档覆盖所有端点
- CHANGELOG 记录所有用户可见变更

## 常见错误


| 错误          | 正确做法         |
| ----------- | ------------ |
| 跳过市场分析直接写代码 | 必须先有需求基础     |
| 开发工程师不写测试   | 每个功能必须有对应测试  |
| 运维工程师不验证部署  | 必须跑通健康检查     |
| 测试经理只写用例不执行 | 必须实际执行并报告结果  |
| 文档与代码脱节     | 每次代码变更同步更新文档 |
| 跳过质量门禁直接发布  | 门禁必须全部通过     |
| 忽略用户反馈      | 反馈必须进入下一迭代   |
| 单次完成不做迭代    | 产品是持续改进的过程   |

## 并行策略详解

### 可并行的 Agent 组合

| 阶段 | 可并行 Agent | 前置依赖 |
|------|-------------|----------|
| 调研 | 市场分析师 + 产品经理 | 无 |
| 执行 | 开发 + 测试 + 运维 + 文档 | 架构设计完成 |
| 验证 | 质量门禁 | 所有执行完成 |

### 不可并行的场景

- 架构师必须等 PRD 初稿
- 测试必须等开发完成
- 质量门禁必须等测试通过
- 部署必须等质量门禁通过
