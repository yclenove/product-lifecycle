# Agent 通信协议

> 多 Agent 协作时的通信方式、文件约定和信息传递规范。

## 1. 通信方式

Agent 间通过文件系统通信，不直接交互。

### 1.1 核心原则

- **文件即接口**：所有 Agent 产出物以文件形式存储在 `docs/` 目录
- **单向传递**：Agent 只写入自己的产出物，不修改其他 Agent 的文件
- **摘要优先**：在 WORKFLOW_PLAN.md 中写摘要，详细内容写入独立文件

### 1.2 通信文件矩阵

| 文件 | 写入者 | 读取者 | 用途 |
|------|--------|--------|------|
| WORKFLOW_PLAN.md | 编排总监 | 所有 Agent | 全局状态和任务分配 |
| docs/MKT-xxx.md | 市场分析师 | 产品经理、编排总监 | 市场分析结果 |
| docs/PRD-xxx.md | 产品经理 | 架构师、开发、测试 | 产品需求 |
| docs/ARCH-xxx.md | 架构师 | 开发、测试、运维 | 架构设计 |
| docs/DEV-xxx.md | 开发工程师 | 测试、质量门禁 | 开发任务清单 |
| docs/QA-xxx.md | 测试经理 | 质量门禁、开发 | 测试结果 |
| docs/QG-xxx.md | 质量门禁 | 编排总监 | 质量审查结果 |
| docs/OPS-xxx.md | 运维工程师 | 编排总监 | 部署报告 |
| docs/DOC-xxx.md | 技术文档师 | 编排总监 | 文档更新记录 |
| docs/SCOUT-xxx.md | 需求侦察兵 | 编排总监、市场分析师 | 侦察报告 |
| docs/FB-xxx.md | 反馈分析师 | 编排总监、产品经理 | 反馈分析 |
| docs/ITER-xxx.md | 迭代规划师 | 编排总监 | 迭代计划 |

## 2. 信息传递格式

### 2.1 摘要格式（写入 WORKFLOW_PLAN.md）

每个 Agent 完成任务后，在 WORKFLOW_PLAN.md 中写入结构化摘要：

```markdown
## [Agent 名称] 摘要
- 状态：完成/进行中/阻塞
- 关键发现：[1-3 条]
- 产出物：[文件路径]
- 下游依赖：[需要哪些 Agent 读取]
```

**示例：**

```markdown
## 市场分析师 摘要
- 状态：完成
- 关键发现：
  - 目标用户：25-35 岁一线城市专业人士
  - 核心竞品：产品 A、产品 B
  - 市场机会：效率工具赛道增长 20%
- 产出物：docs/MKT-001-市场分析报告.md
- 下游依赖：产品经理、编排总监
```

### 2.2 详细输出格式（写入 docs/xxx.md）

遵循对应模板（`templates/xxx_template.md`），包含完整分析和数据支撑。

## 3. 通信规则

### 3.1 路径约定

- 所有产出物写入 `docs/` 目录
- 文件命名遵循编号规范（见 3.2）
- 临时文件使用 `.tmp` 后缀，完成后重命名

### 3.2 编号规范

遵循 `docs/WORKFLOW_DETAILS.md` 中的编号规则：

| Agent | 前缀 | 示例 |
|-------|------|------|
| 市场分析师 | MKT | MKT-001-竞品分析-v0.1 |
| 产品经理 | PRD | PRD-001-Phase1需求-v0.1 |
| 架构师 | ARCH | ARCH-001-系统架构设计-v0.1 |
| 开发工程师 | DEV | DEV-001-功能实现 |
| 测试经理 | QA | QA-001-Phase1测试计划-v0.1 |
| 运维工程师 | OPS | OPS-001-环境部署 |
| 技术文档师 | DOC | DOC-001-API文档 |
| 质量门禁 | QG | QG-001-质量报告 |
| 需求侦察兵 | SCOUT | SCOUT-001-侦察报告 |
| 反馈分析师 | FB | FB-001-反馈分析 |
| 迭代规划师 | ITER | ITER-001-迭代计划 |

### 3.3 版本控制

- 主版本号：重大变更（v1.0, v2.0）
- 次版本号：增量更新（v1.1, v1.2）
- 文件名包含版本号：`MKT-001-市场分析-v1.1.md`

### 3.4 状态标记

在文件头部使用 YAML front matter 标记状态：

```yaml
---
status: completed | in-progress | blocked
version: 1.0
author: 市场分析师
date: 2026-05-05
upstream: [编排总监]
downstream: [产品经理, 编排总监]
---
```

## 4. 通信流程

### 4.1 标准交接流程

```
Agent A 完成任务
    ↓
生成详细产出 → docs/xxx.md
    ↓
生成摘要 → WORKFLOW_PLAN.md
    ↓
更新状态 → status: completed
    ↓
Agent B 读取摘要
    ↓
按需读取详细产出
```

### 4.2 阻塞处理流程

```
Agent A 遇到阻塞
    ↓
更新状态 → status: blocked
    ↓
记录阻塞原因 → WORKFLOW_PLAN.md
    ↓
通知编排总监
    ↓
编排总监协调解决
    ↓
Agent A 继续任务
```

## 5. 上下文管理

### 5.1 摘要优先原则

- 下游 Agent 优先读取 WORKFLOW_PLAN.md 中的摘要
- 仅在需要细节时读取完整文档
- 使用 `grep` 定位关键信息，避免全文读取

### 5.2 信息压缩策略

| 原始大小 | 压缩后 | 方法 |
|----------|--------|------|
| 3000 字 | 300 字 | 提取关键发现和结论 |
| 5000 字 | 500 字 | 保留数据表格，删除说明文字 |
| 10000 字 | 800 字 | 只保留摘要和引用路径 |

### 5.3 上下文预算

每个 Agent 的输入/输出 token 预算（参见 `docs/CONTEXT-MANAGEMENT.md`）：

| Agent | 输入预算 | 输出预算 |
|-------|---------|---------|
| 编排总监 | 8K | 4K |
| 市场分析师 | 12K | 6K |
| 产品经理 | 12K | 8K |
| 架构师 | 16K | 8K |
| 开发工程师 | 16K | 12K |
| 测试经理 | 12K | 6K |

## 6. 错误处理

### 6.1 常见通信错误

| 错误 | 正确做法 |
|------|----------|
| Agent 直接修改其他 Agent 的文件 | 只写入自己的产出物 |
| 未更新 WORKFLOW_PLAN.md 摘要 | 完成后必须更新摘要 |
| 文件命名不符合编号规范 | 遵循 `docs/WORKFLOW_DETAILS.md` 规范 |
| 未标记阻塞状态 | 遇到阻塞立即更新状态 |
| 读取全文而非按需读取 | 先读摘要，按需读取细节 |

### 6.2 状态同步

- 每个 Agent 启动前检查 WORKFLOW_PLAN.md 中的项目状态
- 完成后更新状态和摘要
- 阻塞时通知编排总监

## 7. 最佳实践

### 7.1 文件组织

```
docs/
├── WORKFLOW_PLAN.md          # 全局状态（所有 Agent 读写）
├── MKT-001-*.md              # 市场分析
├── PRD-001-*.md              # 产品需求
├── ARCH-001-*.md             # 架构设计
├── DEV-001-*.md              # 开发任务
├── QA-001-*.md               # 测试结果
├── QG-001-*.md               # 质量门禁
└── ...
```

### 7.2 摘要质量

- 摘要长度：≤200 字
- 包含：状态、关键发现、产出物路径、下游依赖
- 避免：详细分析、代码片段、长段落

### 7.3 版本管理

- 每次重大更新递增版本号
- 保留历史版本（归档到 `docs/archive/`）
- 文件名包含版本号便于追溯

## 8. 工具支持

### 8.1 Claude Code 特性

- **Prompt Caching**：重复读取的文件自动缓存
- **文件搜索**：使用 Grep 定位而非全文读取
- **结构化输出**：使用模板约束输出格式

### 8.2 推荐工作流

```bash
# 1. 读取全局状态
Read WORKFLOW_PLAN.md

# 2. 定位关键信息
Grep "关键决策" docs/

# 3. 按需读取细节
Read docs/PRD-001.md --offset 100 --limit 50

# 4. 输出时使用结构化格式
# 参考模板输出，避免自由文本
```
