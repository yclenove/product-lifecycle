2.1 什么是 Agent

"Agent" 是这两年最火的词之一，但定义混乱。本文先讲业界 3 种主流定义， 再讲本项目里 Agent 具体长什么样、怎么工作、跟单纯调用 API 的区别。

📍 前置阅读 建议先看 1.4 心智模型，建立"公司"直觉。

三种主流定义

定义 1：会"循环 + 工具调用"的 LLM

这是 OpenAI / LangChain 等定义。Agent = LLM + 工具 + 循环。 流程：

  1. 用户给任务
  2. LLM 思考：要不要调工具？调哪个？
  3. 调工具（搜索、计算、读文件…）
  4. 看结果，决定继续调还是回答用户
  5. 循环到完成

定义 2：扮演特定身份的 LLM

Anthropic 倾向这个定义。 Agent = LLM + 一份让它扮演特定角色/任务的长 prompt。 没有循环、没有工具调用也可以叫 Agent。

定义 3：能自主完成多步任务的 LLM

AutoGPT、BabyAGI 流派。Agent = LLM 能自己拆任务、自己执行、自己评估，最少人工干预。

本项目用哪个？

采用定义 2 为主，定义 1 为辅：

  • 每个角色本质是"一份长 prompt"（定义 2）
  • 有些角色允许调工具，比如 market-analyst 用 WebSearch，product-manager 可能用 drawio MCP（定义 1）
  • 不强行追求"完全自主"（不走定义 3 的极端），而是设计成"半自主"——AI 完成任务，人审阅文档

本项目的 Agent 长什么样

打开 agents/product-manager.md，你看到的是这样的结构：

---
description: 产品经理：主动发现需求、定义PRD、用户故事...
tools: Read, Edit, Write, Bash, WebSearch, Grep, Glob
model: ${PL_MODEL_MEDIUM:-claude-3-5-sonnet-latest}
---

# 产品经理 Agent

## 你的核心能力
- 把市场分析转化为可执行的产品需求
- 写出工程师能直接照做的 PRD
- 主动质疑业务诉求的合理性
...

## Step 0：恢复上下文（长程迭代模式）
（自动注入的状态恢复逻辑）

## 应该画的图
- 用户旅程图（mandatory）
- 用户故事地图（recommended）
- 信息架构图（recommended）
（自动注入，优先用 drawio MCP）

## 工作流程
1. 读取上游产出物（市场分析、反馈）
2. ...

## 推荐方法论 skills
- brainstorming
- chinese-documentation

## 产出物
- docs/iterations/current/PRD-XXX-...md
- 必须包含：用户故事、功能列表、验收标准、用户旅程图

组成拆解

① Frontmatter（YAML 元数据）

开头 --- 之间的部分。Claude Code 读取后知道这是什么 Agent、允许它用哪些工具、用哪个模型。

  • description：给编排总监看的"自我介绍"，让它知道什么时候调你
  • tools：白名单。这个 Agent 只能用这些工具
  • model：用哪个模型。${PL_MODEL_MEDIUM:-...} 是环境变量带默认值的写法

② 核心能力 / 职责

用文字描述这个角色"擅长什么"。AI 看到这个会自动调整思维方式。

③ Step 0：恢复上下文

本项目特有。每个 Agent 启动时先检查有没有 STATE.md / HANDOFF.md，有就先恢复"记忆"再干活。这是长程迭代的关键。

④ 应该画的图

本项目特有。明确告诉 Agent："你这个角色必须画 X 图，建议画 Y 图。优先用 drawio MCP，备选 Mermaid。"

⑤ 工作流程

分步骤的操作指令。AI 按这个顺序干。

⑥ 推荐方法论 skills

引用通用工作方法。比如开发类角色推荐读 TDD skill。

⑦ 产出物

明确"做完后要交付什么文件、放在哪里、必须包含什么"。这是产物契约。

Agent 跟普通对话的区别

方面跟 Claude 直接聊天调用本项目的 Agent
身份 通用助手 特定角色（产品经理 / 架构师 / ...）
产出 聊天记录 结构化文档（按模板）
工具权限 所有可用工具 白名单限制
记忆 当次对话 跨 session（通过 STATE.md）
验收 你自己判断 质量门禁自动检查
协作 无 读其他角色的产出，给下一个角色铺路

Agent 不是 AI

再强调一遍：Agent ≠ AI 模型。 Agent 是"给 AI 戴的一顶帽子"。 底层还是 Claude / GPT，但戴上"架构师"的帽子，它就只想架构的事。

为什么不直接给 Claude 全权 prompt？

有人会想："我把所有 20 个角色 prompt 合并成一份大 prompt，一次性给 Claude，不就一步到位？"

试过的都知道：不行。原因：

  1. 注意力稀释：prompt 太长，AI 抓不住重点
  2. 角色串味：写市场分析时跑去写代码，写代码时回头改需求
  3. 无法并行：合并后只能线性走
  4. 无法 review：一坨输出没法分阶段把控
  5. 无法回滚：发现 PRD 有问题，要全部重做
  6. token 浪费：每次都要传 20 倍内容

本项目 Agent 的设计原则

① 单一职责

一个 Agent 只干一件事。"产品经理"不写代码，"架构师"不画 UI。

② 契约清晰

每个 Agent 的输入（读什么文件）、输出（写什么文件）、必含内容（哪些章节）都写明。

③ 可组合

编排总监可以挑子集。20 个全用是上限，最少 2 个也能跑（编排+开发）。

④ 可观测

所有产出是 markdown 文件，能看、能 diff、能 commit。

⑤ 可恢复

支持长程迭代。Step 0 强制读 STATE.md。

Agent 的局限性

Agent 不能做什么
  • 不能跨过它的工具白名单（产品经理不能直接 git commit）
  • 不能凭空获取项目外的真实数据（除非允许 WebSearch）
  • 不能保证 100% 不出错（人 review 必不可少）
  • 不能替代你的判断（Agent 写的 PRD 你还要看、改）

动手感受一下

最快的方式：

# 1. clone 项目
git clone https://github.com/yclenove/product-lifecycle.git
cd product-lifecycle

# 2. 看一个具体的 Agent 文件
cat agents/product-manager.md

# 3. 找差异：跟 architect.md 对比
diff agents/product-manager.md agents/architect.md

你会发现两者结构相同，但每个章节内容完全不同。这就是"换帽子"的本质。

⚡ 进阶：Agent 和 Multi-agent System

学术上叫 Multi-agent System（MAS）。本项目算 cooperative MAS—— Agent 之间合作（不是博弈/对抗）。 跟 MetaGPT、ChatDev、AutoGen 是同类项目。
