心智模型：把它当作公司

建立一个直觉模型很重要。如果你把这套东西想象成"AI 帮你开一家产品公司"， 所有概念都会变得自然。本文用 5 分钟建立这个直觉。

类比：你刚开了一家小公司

想象：你有个产品想法，找投资人融了一点钱，准备组团队做。你会怎么搭建团队？

大致是这样：

  • 你（CEO / 创始人）—— 拍板的
  • 产品总监（PMO）—— 把控时间、人员、风险
  • 市场 / 研究团队—— 看竞品、调研用户
  • 产品经理—— 写需求文档
  • 设计师—— 画 UI
  • 技术团队—— 架构师、前端、后端、DBA
  • 测试 / QA—— 找 bug
  • 运维—— 上线、保稳定
  • 安全 + 数据 + 文档—— 支持职能

怎么"开会"？

真实公司开 kickoff 会议，产品经理讲需求，架构师讨论方案，工程师认领任务……

本项目里类似流程靠"文档"完成（异步开会）：

  1. 产品经理写 PRD（写完保存到 docs/iterations/current/PRD-001.md）
  2. UI 设计师读 PRD，写设计稿，存到 UI-001.md
  3. 架构师读 PRD + UI，写架构设计，存到 ARCH-001.md
  4. 开发者读 PRD + 架构，开始写代码
  5. 测试经理读 PRD + 架构，写测试计划
  6. 质量门禁检查所有产出物是否合格

这套机制叫"文档驱动"。好处是：

  • 不依赖 AI 的"短期记忆"（context）
  • 人可以中途审阅、修改
  • 下一轮迭代时可以读历史决策
  • 跨 session、跨工具都能工作

谁负责管这个公司？

编排总监（orchestrator）。它就是 CTO + COO 的角色：

  • 诊断当前项目状态（新项目？继续迭代？长程恢复？）
  • 决定调用哪些角色、什么顺序
  • 分配并行任务
  • 遇到阻塞时安排重试或换路径

当你说 /product-lifecycle myapp 时，第一个被叫起来的就是它。

这个比喻在哪里"不准"？

类比是工具，记得跳出来时它的边界：

差异真实公司本项目
员工是同一个人 20 个不同的人 同一个 AI 在切换"扮演"
记忆共享 大家见过面、知道彼此说过什么 Agent 之间只通过文档传递信息
能并行 20 个人同时干活 通常一次一个（也支持并行调度）
会犯错 人会犯错也会自己纠错 AI 会幻觉，需要"质量门禁"主动检查
成本 工资 token 费用 / API 调用

另一个有用的比喻：流水线

把公司比喻换成"流水线"也行：

  • 原料：你的想法
  • 第 1 道工序：市场分析（→ MKT 报告）
  • 第 2 道工序：产品需求（→ PRD）
  • 第 3 道工序：设计（→ UI 稿）
  • 第 4 道工序：架构（→ ARCH 文档）
  • 第 5 道工序：开发（→ 代码）
  • 第 6 道工序：测试（→ QA 报告）
  • 第 7 道工序：部署（→ 上线）
  • 第 8 道工序：反馈（→ FEEDBACK 报告，进入下一轮）

每道工序的"质检员"就是质量门禁 Agent。

什么时候要切换心智？

"公司" 心智用来：理解为什么要分这么多角色、为什么有 PMO、为什么要 review。
"流水线" 心智用来：理解工序顺序、上下游依赖、什么不能并行。
"git 仓库" 心智用来：理解所有产出都是 markdown 文件、可以版本管理、可以分支。

常见误解

误解 1：每个 Agent 是独立 AI 实例

不是。本质上还是你的 Claude / GPT，只是换了 prompt。但因为 prompt 不同，AI 的行为完全不一样。

误解 2：Agent 之间能"对话"

不直接对话。它们通过读对方写出来的文档来"沟通"。这是设计选择，不是技术限制。

误解 3：流水线必须从头走到尾

不必。可以只调用部分角色。小项目就跳过市场分析和 PMO。
