Step 2: 影响分析方法

对每个待改进项，按以下方法进行系统化影响分析：

**2.1 代码影响分析** 


分析步骤：
1. grep 搜索涉及的模块和文件
2. 识别直接依赖（谁调用了被修改的函数/类）
3. 识别间接依赖（依赖链上游）
4. 评估修改范围：单文件 / 单模块 / 跨模块 / 全局

| 修改范围 | 风险等级 | 审查要求 |

|----------|----------|----------|

| 单文件 | 低 | 常规 Code Review |

| 单模块 | 中 | 模块负责人审查 |

| 跨模块 | 高 | 架构师审查 + 集成测试 |

| 全局 | 极高 | 全员审查 + 全量回归测试 |

**2.2 数据影响分析**

| 场景 | 是否需要 Migration | 回滚复杂度 |

|------|-------------------|-----------|

| 新增字段（可空） | 否 | 低 |

| 新增字段（非空） | 是（需默认值） | 中 |

| 修改字段类型 | 是 | 高（需数据转换） |

| 删除字段 | 是（需先停用） | 极高 |

| 新增表 | 否 | 低 |

| 删除表 | 是（需备份） | 极高 |

**2.3 API 影响分析** 


检查清单：
- [ ] 是否新增端点？（向后兼容）
- [ ] 是否修改现有端点的请求参数？（可能破坏客户端）
- [ ] 是否修改现有端点的响应格式？（可能破坏客户端）
- [ ] 是否删除现有端点？（破坏性变更）
- [ ] 是否需要 API 版本号变更？

**2.4 综合影响矩阵**

| 改进项 | 代码范围 | 数据影响 | API 影响 | 测试影响 | 文档影响 | 回归风险 | 综合评级 |

|--------|----------|----------|----------|----------|----------|----------|----------|

| [ID] | 单模块 | 无 | 无 | 中 | 低 | 低 | 低 |

| [ID] | 跨模块 | Migration | 破坏性 | 高 | 高 | 高 | 高 |

**回滚策略选择：**

| 变更类型 | 回滚策略 | 复杂度 |

|----------|----------|--------|

| 代码变更 | Git revert | 低 |

| 数据库变更 | 回滚脚本 + 备份恢复 | 中 |

| API 变更 | 版本回退 + 客户端降级 | 高 |

| 配置变更 | 配置回滚 | 低 |

| 依赖升级 | 锁定旧版本 | 低 |

Step 5: 版本策略

  • Breaking change 必须升 major
  • 新功能升 minor
  • Bug 修复升 patch
