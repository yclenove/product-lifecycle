Step 2: 测试策略

**测试层次（测试金字塔）：** 


        /  E2E  \          ← 少量，验证核心用户场景
       / 集成测试 \         ← 适量，验证模块间交互
      /  单元测试   \       ← 大量，验证函数/方法逻辑

| 层次 | 目的 | 工具 | 数量占比 | 覆盖目标 |

|------|------|------|----------|----------|

| 单元测试 | 验证函数/方法逻辑 | 项目对应框架 | ~70% | 核心逻辑 100% |

| 集成测试 | 验证模块间交互 | 项目对应框架 | ~20% | 关键路径 100% |

| E2E 测试 | 验证用户场景 | 项目对应框架 | ~10% | P0 场景 100% |

| 手动测试 | 验证 UX 和边界 | 人工 | 补充 | 关键场景 |

**测试方法：**

  • 功能测试：验证功能是否符合需求
  • 边界测试：验证边界条件处理
  • 错误测试：验证错误处理和恢复
  • 安全测试：验证认证、授权、数据保护
  • 性能测试：验证响应时间和吞吐量

Step 5: 回归测试策略

**以下改动必须触发回归测试：**

| 改动类型 | 回归范围 | 理由 |

|----------|----------|------|

| 核心业务逻辑变更 | 全量回归 | 影响面最大 |

| 数据库 Schema 变更 | 数据相关模块 | 可能破坏现有查询 |

| API 接口变更 | 所有调用方 | 破坏兼容性风险 |

| 认证/授权变更 | 所有受保护资源 | 安全关键 |

| 依赖库升级 | 使用该库的模块 | 可能有 breaking change |

| 配置变更 | 相关功能 | 环境差异 |

**回归测试优先级：**

  • 1. P0 用例全量执行
  • 2. 受影响模块的 P1 用例
  • 3. 冒烟测试覆盖其他模块
