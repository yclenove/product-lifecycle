# Worked Example: SaaS 产品持续迭代

> 使用 product-lifecycle 模式 B（持续迭代）驱动已上线 SaaS 协作工具的版本升级。
> 注：本例为虚构项目，用于演示模式 B 完整流程。

## 项目背景

- **产品名：** TeamSync
- **描述：** 在线团队协作 SaaS 工具，包含任务管理、文档协作、即时通讯
- **现状：** 已上线 6 个月，MAU 2000+，基础功能稳定
- **技术栈：** Node.js + React + PostgreSQL + Redis
- **部署：** AWS ECS + RDS

## 触发条件

**用户反馈（反馈分析师收集）：**
- 高频需求：多人实时编辑文档冲突率 15%（NPS 调研中被提及 47 次）
- Bug 报告：移动端任务拖拽偶发卡顿（GitHub Issue #342）
- 竞品动态：竞品 Notion-like 编辑器已上线 AI 摘要功能

**产品体检（需求侦察兵发现）：**
- 文档模块 DAU 环比下降 8%（可能因冲突体验差）
- API 响应时间 P95 从 200ms 升至 350ms（需排查）

## 执行过程

### Phase 1: 侦察与反馈收集（20 分钟）

**需求侦察兵：**
- WebSearch: "real-time collaboration CRDT algorithm 2025"
- 产品健康检查：分析 DAU 下降趋势，定位文档模块
- 产出：侦察报告，2 个机会 + 1 个风险

**反馈分析师：**
- 汇总 GitHub Issues（42 条）、用户访谈记录（5 份）、NPS 评论（120 条）
- 聚类分析：实时协作冲突（47 次提及）> 移动端性能（23 次）> AI 功能（18 次）
- 产出：反馈分析报告，按优先级排序的改进清单

### Phase 2: 市场与需求分析（25 分钟）

**市场分析师：**
- WebSearch: "Notion alternative real-time editing 2025"
- WebFetch: 分析竞品 Coda、Notion 的编辑器架构公开资料
- 产出：市场分析报告，竞品编辑器对比矩阵

**产品经理：**
- 综合反馈分析 + 市场分析，定义 v2.0 迭代范围
- P0：文档实时协作优化（CRDT 方案）
- P0：移动端性能优化
- P1：AI 文档摘要（MVP）
- 产出：PRD v2.0，8 个功能项，验收标准

### Phase 3: 迭代规划（15 分钟）

**迭代规划师：**
- 读取 PRD + 反馈分析报告 + 架构设计（已有）
- 影响分析：CRDT 改造影响文档存储层（3 个 API 变更）
- 迭代计划：2 个 Sprint，Sprint 1 处理 P0，Sprint 2 处理 P1
- 回滚方案：文档编辑器灰度发布，保留旧编辑器 1 个版本
- 产出：迭代计划文档

### Phase 4: 架构评估（15 分钟）

**架构师：**
- 影响分析：CRDT 引入需新增 WebSocket 通道 + 冲突合并服务
- 评估 Yjs vs Automerge，推荐 Yjs（更成熟的协作生态）
- 数据模型变更：documents 表新增 version_vector 字段
- 产出：技术设计补丁（增量文档，非重写）

### Phase 5: 开发实现（60 分钟）

**开发工程师：**
- Sprint 1：CRDT 编辑器集成 + WebSocket 通道 + 移动端拖拽优化
- Sprint 2：AI 摘要 API 接入（调用 Claude API）
- 单元测试：22 个新用例，覆盖率 85%

### Phase 6: 测试与质量审查（30 分钟）

**测试经理：**
- 回归测试：68 个已有用例全部通过
- 新功能测试：CRDT 冲突场景 12 个用例（2 人并发、断网重连、离线编辑）
- 性能测试：移动端拖拽帧率从 30fps 提升至 55fps
- 产出：测试报告

**质量门禁：**
- 代码审查：CRDT 模块引入 3 个新的并发安全问题，要求修复
- 安全审查：WebSocket 认证机制审查通过
- 产出：质量报告

### Phase 7: 发布（10 分钟）

- 更新 CHANGELOG.md（v2.0 变更记录）
- 灰度发布：10% 用户先行
- 监控指标：文档冲突率、API P95 响应时间

## 关键决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 实时协作算法 | Yjs (CRDT) | 社区活跃、性能好、与 ProseMirror 集成成熟 |
| AI 摘要方案 | Claude API | 成本可控、中文效果好、无需自建模型 |
| 发布策略 | 灰度 10% | CRDT 改造风险高，需逐步验证 |
| Sprint 划分 | P0 先行、P1 跟进 | 冲突率是用户流失主因，优先解决 |

## 经验总结

1. **自驱动 Agent 的价值**：需求侦察兵主动发现 DAU 下降趋势，比人工复盘早 2 周
2. **增量设计优于重写**：架构师产出「技术设计补丁」而非重写整个架构文档，节省 50% 时间
3. **回滚方案必须前置**：迭代规划师在规划阶段就定义灰度策略，发布时直接执行
